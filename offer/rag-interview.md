## 一、RAG 基础概念

### Q1 🟢 什么是 RAG（检索增强生成）？它与直接使用 LLM 相比有什么本质优势？

**考察点**：对 RAG 范式的理解

**参考答案**：

RAG = Retrieval（检索） + Augmented（增强） + Generation（生成）

核心思想：在生成回答前，先从外部知识库中检索相关文档片段，把它们作为上下文一起喂给 LLM，让 LLM 基于「检索到的事实」而不是「训练数据里的记忆」来回答。

| 维度 | 纯 LLM | RAG |
|------|--------|-----|
| 知识来源 | 训练数据（截止日期前） | 外部知识库（可实时更新） |
| 事实性 | 易幻觉，编造事实 | 基于检索到的原文，有据可查 |
| 知识更新 | 需要重新训练 / 微调 | 新增文档即可，无需重新训练 |
| 可追溯性 | 黑盒，无法验证答案来源 | 可溯源到具体文档片段 |
| 私有知识 | 无法处理（除非微调） | 天然支持私有知识库 |
| 成本 | 仅推理成本 | 检索成本 + 推理成本 |

**RAG 的三大价值**：
1. **减少幻觉**：生成基于事实文档，而非模型记忆
2. **知识时效性**：知识库更新即可获取最新信息
3. **私有化部署**：支持企业内部知识库问答

**基础 RAG 流程**：
```
用户提问 → Query Embedding → 向量检索 → TopK 文档片段 →
拼成 Prompt（System + Context + Question）→ LLM 生成 → 返回答案
```

### Q2 🟢 解释 RAG 的「离线」与「在线」两个阶段，各阶段核心做什么？

**考察点**：RAG 两阶段流程理解

**参考答案**：

**离线阶段（Ingestion / 构建索引）**——「建库」：

```
原始文档 → 加载 → 分块 → Embedding → 写入向量数据库
```

- **文档加载**：PDF/Word/Markdown/HTML/网页 → 提取纯文本
- **文本分块（Chunking）**：长文档切分为语义完整的小块（如 512 tokens）
- **Embedding 向量化**：用 Embedding 模型将每个 Chunk 转为向量
- **索引存储**：向量 + 元数据（原文、来源、页码等）写入向量数据库（Milvus / FAISS / Chroma / PGVector）

关键：离线做得好，在线才能答得准。分块策略、Embedding 模型选择直接决定检索质量上限。

**在线阶段（Query / 问答）**——「回答」：

```
用户 Query → Embedding → 向量检索（+关键词检索）→ 重排序 →
上下文压缩 → 组装 Prompt → LLM 生成 → 返回答案
```

- **Query 改写**：把用户口语化问题转为更适合检索的形式
- **多路召回**：向量检索 + BM25 关键词检索，扩大召回面
- **重排序（Rerank）**：用 Cross-Encoder 对召回结果精排
- **上下文压缩**：去除冗余，只保留与问题最相关的片段
- **生成回答**：LLM 基于压缩后的上下文生成答案

### Q3 🟡 RAG 中「检索」和「生成」分别会导致什么典型的 Bad Case？如何排查？

**考察点**：RAG 问题定位能力

**参考答案**：

RAG 回答质量问题 = 检索问题 或 生成问题，需先定位是哪一层出的问题。

**典型排查流程**：
```
用户说答案不对 → 先看检索到的文档是否包含正确答案？
  ├─ 检索不到 → 检索问题（召回不足 / 排序错误）
  └─ 检索到了但 LLM 没用上 / 用错了 → 生成问题
```

**1. 检索层问题**：

| 现象 | 原因 | 排查方法 |
|------|------|----------|
| 文档里有答案但没检索到 | 召回不足 | 看 topK 是否有答案；扩大 topK 观察；换 embedding 模型 |
| 检索到了但排在很后面 | 排序错误 | 加 rerank；调混合检索权重 |
| 检索到无关文档 | 精度不足 | 分块太大/太小；Query 语义歧义 |
| 同义/近义词召回差 | 向量检索语义边界模糊 | 加 BM25 互补；调 alpha 权重 |

**2. 生成层问题**：

| 现象 | 原因 | 排查方法 |
|------|------|----------|
| 检索到正确片段但 LLM 没引用 | Lost in the middle（中间遗忘） | 排序最相关的放最前/最后；减少上下文长度 |
| 引用了但理解错误（断章取义） | 片段缺少上下文 | 分块时加 overlap；用父文档检索 |
| 幻觉出文档中没有的信息 | 模型本身幻觉；Prompt 约束不够 | Prompt 加「仅基于以下文档回答，不知道就说不知道」；加引用校验 |
| 格式不符合要求 | Prompt 格式引导不足 | Few-shot 示例；JSON mode / Structured Output |

**3. 端到端评估**：
- **Recall@K**：正确文档是否在 TopK 召回中（检索召回率）
- **MRR**：正确文档的排序位置倒数平均值（排序质量）
- **Faithfulness**：生成内容是否都能在上下文中找到依据（忠实度）
- **Answer Relevance**：生成答案是否切题（答案相关性）

## 二、文档处理与分块（Chunking）

### Q4 🟡 为什么需要文本分块（Chunking）？有哪些常见的分块策略？各适用于什么场景？

**考察点**：分块策略的理解与选型

**参考答案**：

**为什么要分块**：
1. **Embedding 模型有最大输入长度限制**（如 text-embedding-ada-002 限 8191 tokens），超长文档无法直接 Embedding
2. **检索粒度问题**：整本书 Embedding 成一个向量，任何问题都可能匹配到它，但它太长无法作为上下文喂给 LLM
3. **上下文窗口限制**：LLM 上下文窗口有限（如 128K），需要把检索到的片段塞进去
4. **语义聚焦**：小块语义更单一，Embedding 更精准，检索匹配度更高

**常见分块策略**：

| 策略 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| **固定大小分块** | 按固定字符/token 数切分，加 overlap | 简单，开销低 | 可能切断语义单元（如一段中间切开） | 通用默认，快速验证 |
| **按结构分块** | 按 Markdown 标题 / HTML 标签 / 段落切分 | 尊重文档结构，语义完整 | 依赖格式规范，非结构化文档难用 | Markdown/HTML/LaTeX 等结构化文档 |
| **递归字符分块** | 优先按 `\n\n` → `\n` → `.` → ` ` → 字符切分，直到满足块大小 | 比固定大小更尊重边界 | 仍可能切断语义 | LangChain 默认，通用场景 |
| **语义分块（Semantic Chunking）** | 用 embedding 相似度，相邻句子相似度下降时切分 | 按语义边界切，不破坏语义单元 | 速度慢，需 embedding 模型；对长连续语义效果不稳定 | 对检索精度要求高，文档语义边界清晰 |
| **基于 Token 的分块** | 用 Tokenizer 精确计数切分 | Token 数精确，不浪费上下文窗口 | 仍可能切断语义 | 需要精确控制块大小时 |

**最佳实践**：
```typescript
// 推荐：结构化优先 + 回退策略
function smartChunk(doc: Document): Chunk[] {
  if (isMarkdown(doc)) {
    return chunkByMarkdownHeadings(doc, { maxTokens: 512 });
  }
  // 回退：递归字符分块 + 10% overlap
  return recursiveCharChunk(doc, {
    chunkSize: 512,
    chunkOverlap: 50,
    separators: ['\n\n', '\n', '.', ' ', ''],
  });
}
```

### Q5 🔴 分块时 chunkSize 太大或太小各有什么问题？如何选择最佳分块大小？

**考察点**：Chunking 参数调优

**参考答案**：

**ChunkSize 太大**：
```
问题：
1. 单个 Chunk 包含多个主题 → Embedding 「语义稀释」，检索不准
   （一篇文章同时讲「RAG 分块」和「向量数据库」，向量会变成混合主题）
2. 检索到后，上下文窗口塞不了几个 chunk → 覆盖面不足
3. 无关内容多 → 增加 LLM 上下文噪声，Lost in the middle 更严重
4. Token 浪费 → 推理成本上升
```

**ChunkSize 太小**：
```
问题：
1. 单个 Chunk 语义不完整 → Embedding 缺乏上下文，匹配不准
   （「它的发病率约 5%」→ 不知道「它」指什么病）
2. 需要召回更多 chunk 才能覆盖答案 → 增加检索/rerank 开销
3. LLM 拼接多个片段时缺乏上下文衔接 → 断章取义
```

**选择最佳大小的方法**：

| 维度 | 推荐 |
|------|------|
| **黄金标准**：平均答案在多少 tokens 内能覆盖 | chunkSize ≈ 答案长度 × 3-5（留足上下文） |
| **Embedding 模型上下文** | ≤ 模型最大输入的 1/4（避免截断） |
| **LLM 上下文窗口** | TopK × chunkSize ≤ 窗口可用空间的 30-40%（留空间给 Prompt + History） |
| **经验值**：通用问答 | 300-800 tokens，overlap 10-20% |
| **经验值**：代码检索 | 200-400 tokens（函数级），overlap 50 tokens（保留函数签名） |
| **经验值**：长文档总结问答 | 1000-2000 tokens |

**定量调优**：
1. 准备标注集：（Query, 黄金文档片段）
2. 对不同 chunkSize 跑 Recall@5 / MRR
3. 取曲线拐点最优解（chunkSize 增大但 Recall 不再提升时停止）

**进阶：父子分块（Parent-Child Chunking）**：
```
父文档（大 chunk，如 2000 tokens）：用于 LLM 生成，提供完整上下文
  ├─ 子文档 1（小 chunk，如 200 tokens）：Embedding 用于检索
  ├─ 子文档 2（小 chunk，200 tokens）
  └─ ...

检索时：子文档匹配 → 找到对应的父文档 → 返回父文档给 LLM
兼顾检索精度（小子块语义明确）和生成质量（大父块上下文完整）
```

### Q6 🟡 如何处理 PDF / 图片 / 表格等非纯文本格式？

**考察点**：多模态文档处理

**参考答案**：

| 格式 | 处理方案 |
|------|----------|
| **PDF（文本型）** | PyMuPDF / pdfplumber 提取文本 + 元数据（页码、字体大小用于识别标题） |
| **PDF（扫描件）** | OCR：PaddleOCR / Tesseract / 商业 API（AWS Textract）。进阶：LayoutLM 识别版式 |
| **Word / PPT** | python-docx / python-pptx 提取文本，保留段落结构 |
| **HTML / 网页** | BeautifulSoup / Readability.js 去噪（去掉导航栏、广告），保留 `<h1>` 等结构 |
| **Markdown** | 直接按标题结构分块，保留代码块和表格 |
| **表格（Excel/CSV）** | 方案 1：转 Markdown 表格文本；方案 2：行/单元格级分块 + 保留表头上下文；方案 3：结构化存储，支持 SQL 查询 |
| **图片** | 方案 1：多模态 Embedding（CLIP / BLIP）直接向量化；方案 2：OCR 提取文字 + image caption 生成描述；方案 3：分块时附图片引用链接，生成时用多模态 LLM（GPT-4V）理解 |
| **音视频** | Whisper 转文字，按说话人/时间戳分块；保留时间戳用于跳回原视频 |

**表格处理难点**：
```
原始表格：
| 产品 | Q1 销量 | Q2 销量 |
|------|---------|---------|
| A    | 100     | 150     |
| B    | 200     | 180     |

转文本后直接喂给 LLM 效果差，因为：
1. 表格结构丢失
2. 用户问「Q2 哪个产品销量最高」→ 需要理解行列关系

最佳实践：
1. 保留 Markdown 表格格式（LLM 对 Markdown 表格理解较好）
2. 每行带表头上下文：「产品 A: Q1销量=100, Q2销量=150」
3. 复杂表格：提前做结构化处理，用 Text-to-SQL 而非纯文本检索
```

## 三、Embedding 与向量检索

### Q7 🟢 什么是 Embedding？为什么向量能表示语义？常见的相似度计算方式有哪些？

**考察点**：向量基础

**参考答案**：

**Embedding（嵌入/向量化）**：用一个低维稠密向量（如 1536 维 float）来表示一段文本的语义。语义相似的文本，向量在高维空间中距离更近。

**为什么向量能表示语义**：
Embedding 模型（如 BGE, text-embedding-3）在海量文本上通过对比学习训练：
- 给定「正样本对」（语义相似的文本，如 Query 和对应的文档）→ 拉近它们的向量距离
- 给定「负样本对」（语义不同的文本）→ 推远它们的向量距离
- 训练完成后，模型学会了把「语义相近」映射为「空间相近」

```
例：
「苹果手机怎么刷机」 → 向量 A
「iPhone 如何重装系统」 → 向量 B  ← 与 A 距离近（语义相近）
「苹果水果多少钱一斤」 → 向量 C  ← 与 A 距离远（消歧能力）
```

**常见相似度计算**：

| 方式 | 公式 | 取值范围 | 特点 | 适用场景 |
|------|------|----------|------|----------|
| **Cosine Similarity（余弦相似度）** | `cos(a,b) = a·b / (|a|·|b|)` | [-1, 1]，越大越相似 | 不关心向量长度，只关心方向；最常用 | 文本相似度（文本长短不同但语义相同，长度不同但方向一致） |
| **Dot Product（点积）** | `a·b = Σaᵢbᵢ` | (-∞, +∞)，越大越相似 | 考虑向量长度；已归一化的向量等价于 cosine | 推荐系统（向量长度可表示流行度） |
| **L2 Distance（欧氏距离）** | `||a-b||₂` | [0, +∞)，越小越相似 | 几何距离，简单直观 | 图像检索；聚类 |
| **Inner Product（内积）** | 同道积 | - | - | 部分向量数据库的底层实现 |

**关系**：如果向量做了 L2 归一化（|a|=1, |b|=1），则 Cosine = Dot Product。多数 Embedding 模型输出后会先归一化，所以实际场景中 Cosine 和 Dot Product 效果一致。

### Q8 🟡 如何选择 Embedding 模型？中英文场景有什么差异？

**考察点**：Embedding 模型选型

**参考答案**：

**选型维度**：

| 维度 | 说明 |
|------|------|
| **语言** | 中文优先用中文优化的模型（BGE / M3E / GTE） |
| **维度** | 通常 768 / 1024 / 1536 维。维度越高精度越好，但存储和计算成本线性增长。768 维是性价比之选 |
| **最大输入长度** | 常见 512 / 8191 / 32K tokens。长文档优先选长上下文模型 |
| **评测分数** | 看 MTEB（英文）/ C-MTEB（中文）榜单 |
| **部署成本** | 开源模型 vs API；参数大小（BGE-base 110M vs BGE-large 335M） |
| **License** | 商用需注意（部分模型非商用免费，商用需授权） |

**中英文差异**：

| 模型 | 语言 | 特点 |
|------|------|------|
| text-embedding-3-small/large | 多语言 | OpenAI API，英文强，中文一般；省心但按 token 收费 |
| BGE / BGE-M3 | 中文 | 中文场景最强开源选择之一；M3 支持多粒度（短句/长文/跨语言） |
| GTE | 中文 | 阿里出品，中文效果好，有量化版本 |
| M3E | 中文 | 中文通用嵌入，适合中文检索场景 |
| text-embedding-v2 | 多语言 | 通义千问 API，中文效果好 |

**选型建议**：
```
通用场景（中英文混合）：
- 预算充足 → text-embedding-3-large（API，省心）
- 需本地化部署 → BGE-M3（支持长文，中英文混合效果好）

纯中文场景：
- BGE-large-zh v1.5 → 精度最佳
- 对性能敏感 → BGE-base-zh v1.5（小 3 倍，精度损失有限）

代码检索：
- CodeBERT / StarCoder Embedding → 对代码语义特化
```

**验证方法**：不要光看榜单，用自己的数据做 A/B 测试：
1. 准备 100+ 标注对（Query, 正确文档）
2. 用不同模型 Embedding
3. 跑 Recall@5 / MRR
4. 选自己业务上效果最好的

### Q9 🔴 向量数据库是怎么做到「从亿级向量中毫秒级召回相似向量」的？核心索引原理是什么？

**考察点**：ANN 索引理解

**参考答案**：

核心是 **ANN（Approximate Nearest Neighbor，近似最近邻）**——用 1-5% 的精度损失换取 100-1000 倍的速度提升。

**为什么不用暴力搜索**：
暴力搜索 = Query 向量与所有向量逐一计算相似度，O(N) 复杂度。亿级向量单条 Query 需要几秒到几十秒，不可接受。

**主流 ANN 索引算法**：

#### 1. HNSW（Hierarchical Navigable Small World）—— 最主流

**原理**：多层有向图 + 贪心搜索

```
Layer 2（最上层，稀疏）:   ○──○        只有少数节点，用于快速「跳」到大致区域
                              ╲╱
Layer 1（中间层）:         ○──○──○──○   中等密度
                           ╱  ╲╱  ╲
Layer 0（最底层，稠密）: ○──○──○──○──○  所有节点都在这层，精细搜索
```

- **构建**：新节点随机选一个 level（概率衰减），在每层与最近的 M 个邻居连边
- **搜索**：从最上层入口节点开始贪心找最近 → 下降到下层重复 → 最底层找到 TopK
- **复杂度**：O(log N) 跳数，每跳只算几次相似度

**优点**：召回率高、速度快、内存友好、支持增量插入
**缺点**：构建时间较长（需建图）、删除困难（需标记墓碑）、不适合动态更新极频繁场景

#### 2. IVF（Inverted File Index）—— 倒排索引

**原理**：聚类 + 倒排

```
Step 1: 用 K-Means 把所有向量聚成 nlist 个簇，每个簇有「质心向量」
        簇0（质心 C0）  簇1（质心 C1）  ...  簇1023
        [v1, v5, v9]   [v2, v3, v7]        [v4, v6, v8]

Step 2: 搜索时，Query 先找最近的 nprobe 个质心（如找 32 个最近簇）
        → 只在这些簇内做暴力搜索
        → 原本搜 1亿，现在搜 1亿 / 1024 × 32 ≈ 300万，快 30 倍
```

**优点**：构建快、索引占用小、训练和搜索可解耦
**缺点**：nprobe 太小召回差、太大速度慢；需调参平衡；边界附近向量可能被误判到其他簇

#### 3. DiskANN（基于磁盘的 ANN）—— 超大向量规模

**原理**：把索引和向量存在 SSD 上，内存只缓存热点节点，适合十亿级向量单机部署。

**选型对比**：

| 算法 | 召回率 | 速度 | 内存 | 构建速度 | 增量更新 | 适用场景 |
|------|--------|------|------|----------|----------|----------|
| HNSW | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 较高 | 较慢 | ⭐⭐⭐⭐ | 默认首选，百万-千万级 |
| IVF | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 低 | 快 | ⭐⭐⭐ | 亿级，成本敏感 |
| DiskANN | ⭐⭐⭐⭐ | ⭐⭐⭐ | 极低 | 中等 | ⭐⭐⭐ | 十亿级，单机 |

**关键参数调优**：
- HNSW：`M`（每个节点邻居数，默认 16-64，越大精度越高越慢）、`efConstruction`（构建时搜索宽度，默认 200-400）、`efSearch`（查询时搜索宽度，越大精度越高越慢）
- IVF：`nlist`（簇数，√N 起步）、`nprobe`（搜多少簇，越大精度越高越慢）

## 四、混合检索与重排序（Hybrid & Rerank）

### Q10 🟡 什么是混合检索（Hybrid Search）？为什么单纯向量检索不够？

**考察点**：混合检索的理解

**参考答案**：

**混合检索** = 向量检索（语义匹配）+ 关键词检索（精确匹配，通常 BM25），两路召回后融合排序。

**为什么纯向量检索不够**：

| 场景 | 向量检索表现 | BM25 表现 |
|------|-------------|----------|
| 「张三的身份证号是多少」（精确人名/ID） | 可能召回其他「张三」的文档，歧义 | 精确命中含「张三 + 身份证号」的片段 |
| 「file_path = config.yaml 的第 20 行」（专有名词/代码符号） | 语义相近但符号不同的容易混 | 精确匹配符号 `config.yaml` |
| 「推荐几款适合学生的笔记本电脑」（自然语言意图） | ✅ 能匹配「高性价比学生电脑推荐」 | ❌ 不含「笔记本电脑」关键词的可能漏 |
| 「RAG 分块策略最佳实践」 | ✅ 召回「RAG Chunking 技巧」（同义词匹配） | ❌ 不含「策略/最佳实践」精确词的文档会漏 |

**结论**：向量检索擅长**语义模糊匹配**，BM25 擅长**精确关键词匹配**，两者互补。

**混合检索实现方式**：

**方式 1：加权分数融合（最简单）**
```typescript
// 两路召回 TopN，各自归一化分数后加权求和
const alpha = 0.5; // 0 = 只用 BM25, 1 = 只用向量
const bm25Scores  = normalizeMinMax(bm25.search(query, 50));   // 归一化到 [0,1]
const vecScores   = normalizeMinMax(vector.search(query, 50)); // 归一化到 [0,1]

const merged = new Map();
for (const [id, score] of bm25Scores) {
  merged.set(id, (1 - alpha) * score);
}
for (const [id, score] of vecScores) {
  merged.set(id, (merged.get(id) ?? 0) + alpha * score);
}
// 按总分排序取 TopK
```

**方式 2：RRF（Reciprocal Rank Fusion，推荐）**
```
不依赖原始分数量纲，只看排名，更鲁棒
RRF 公式：score = Σ 1 / (k + rank)，k 通常取 60

例：
文档 A 在 BM25 排第 1，在向量检索排第 3 → 1/(60+1) + 1/(60+3) ≈ 0.0164 + 0.0159 = 0.0323
文档 B 在 BM25 排第 10，在向量检索排第 1 → 1/(60+10) + 1/(60+1) ≈ 0.0143 + 0.0164 = 0.0307
→ 文档 A 胜出（排名综合更靠前）
```

RRF 优势：
- 不关心原始分数是 0.8 还是 80，只看排名，避免不同算法分数量纲差异
- 对分数字段异常鲁棒（某一路分数整体偏高/偏低不影响）
- 实践中通常优于简单加权

**Alpha 调优经验**：
- 代码检索、专有名词多 → alpha 调低（加大 BM25 权重）
- 自然语言、FAQ → alpha 调高（加大向量权重）
- 没有先验 → alpha=0.5 起步，A/B 测试调整

### Q11 🔴 什么是 Reranker（重排序）？为什么不直接在召回阶段把排序做好？

**考察点**：Rerank 阶段的必要性

**参考答案**：

**召回 → 粗排 → 精排（Rerank）** 是搜索系统的经典三阶段漏斗：

```
[召回] 100 万文档 → 粗排 Top100 → 精排（Rerank）Top10 → 给 LLM
   ↑ 速度优先         ↑ 精度+速度平衡    ↑ 精度优先
   ANN/倒排          简单打分模型         Cross-Encoder / 大模型
   毫秒级            十毫秒级             百毫秒级（慢但准）
```

**为什么召回阶段不能直接排好**：

| 阶段 | 模型类型 | 能力差异 |
|------|----------|----------|
| 召回 | Bi-Encoder（双塔模型，如 BGE Embedding） | Query 和文档各自独立做 Embedding，然后算相似度。优点是可预计算缓存，快。缺点是 Query 和文档交互仅发生在最后一步点积，匹配精细度有限。 |
| Rerank | Cross-Encoder（交叉编码器，如 BGE Reranker） | Query 和文档拼接后一起送入 Transformer，在每一层自注意力中充分交互。精度明显更高，但不能预计算，每个 Query-文档对都要单独推理，慢。 |

**通俗理解**：
- Bi-Encoder = 先各自读完，闭卷考试，答完对答案 → 快但粗
- Cross-Encoder = 两个人一起讨论后得出结论 → 慢但准

**典型流水线**：
```typescript
async function hybridRAGSearch(query: string, topK = 5) {
  // 1. 双路召回扩大候选集（高召回，低精度）
  const bm25Candidates = bm25.search(query, 50);    // 50 个
  const vecCandidates  = await vector.search(query, 50); // 50 个

  // 2. RRF 合并 + 去重
  const merged = rrfMerge(bm25Candidates, vecCandidates); // 约 80 个

  // 3. Rerank 精排（高精度，慢）
  // 把 (Query, 文档) 一对对送进 Cross-Encoder 打分
  const reranked = await reranker.rerank(query, merged, { returnTopK: 20 });

  // 4. 上下文压缩（可选，进一步精简）
  const compressed = await contextCompressor.compress(query, reranked.slice(0, topK * 2));

  // 5. 最终 TopK 给 LLM
  return compressed.slice(0, topK);
}
```

**Reranker 选型**：

| 模型 | 特点 | 适用 |
|------|------|------|
| BGE Reranker v2 (bge-reranker-v2-m3) | 中文效果好，支持长文本 | 中文 RAG 默认 |
| bge-reranker-large | 精度最高，速度慢 | 对精度要求高 |
| bge-reranker-base | 速度快，精度略低 | 对延迟敏感 |
| Cohere Rerank API | 英文强，API 调用 | 英文场景 + 不想自己部署 |
| LLM 作为 Reranker | 用 GPT-4/ Claude 做「选出最相关的 3 段」 | 候选集很小（<10 个），精度极致追求 |

**延迟优化**：
- Rerank 是整个检索流水线最慢的一步
- 控制精排文档数：通常 50-100 个候选进入 rerank
- 量化模型（INT8/FP16）+ GPU 推理加速
- 对高频 Query 的 rerank 结果做缓存

### Q12 🔴 Query 改写（Query Transformation）有哪些常用手段？分别解决什么问题？

**考察点**：查询侧优化

**参考答案**：

用户原始 Query 往往不适合直接检索（口语化、歧义、上下文依赖、缺少约束），需要改写后再检索。

**常用改写手段**：

#### 1. Query 扩写（Query Expansion）
```
用户：「怎么刷手机」
  → 扩展：「智能手机刷机教程 + 安卓 root 方法 + 手机系统重装」

方法：
- 同义词词典：手机=智能手机=移动电话
- LLM 扩写：让 LLM 根据原始 Query 生成 3-5 个同义改写
- Pseudo Relevance Feedback：先检索 Top3，从高分文档中提关键词补充回 Query
```
**解决问题**：用户用词与文档词汇不匹配（同义/近义）

#### 2. 子问题拆解（Sub-Query Decomposition）
```
用户：「RAG 怎么同时处理中英文文档并降低幻觉」
  → 拆解：
     Q1: RAG 中英文混合处理方案
     Q2: RAG 减少幻觉的方法
  → 分别检索后合并结果
```
**解决问题**：复杂多意图问题，单一检索覆盖面不足

#### 3. 引用补全（Contextual Query Rewrite）
```
多轮对话场景：
用户 1：「RAG 分块最佳大小是多少？」→ 回答
用户 2：「那 overlap 呢？」
  → 第 2 个问题单独检索会搜出「overlap 什么意思」等无关结果
  → 改写：「RAG 分块中 overlap 的最佳设置是多少」

方法：把最近对话历史 + 当前 Query 拼给 LLM，让 LLM 输出「去上下文依赖」后的独立查询
```
**解决问题**：多轮对话中当前 Query 有指代/省略/上下文依赖

#### 4. 假设性文档生成（HyDE - Hypothetical Document Embedding）
```
用户：「RAG 分块最佳大小？」
  → 先让 LLM 生成一个「假设的理想答案」（不用对，只要语义像）：
     「RAG 分块大小通常设为 300-800 tokens，取决于 LLM 上下文窗口和 Embedding 模型...」
  → 把这个「假设答案」做 Embedding 去检索（而不是原始 Query）

原理：Query 短（问题），文档长（答案），直接 Embedding 空间有 Gap；
      假设答案是长文本，和真实文档空间更接近，匹配度更高。
```
**解决问题**：短 Query 与长文档的向量空间分布差异

#### 5. 结构化提取（Structured Query）
```
用户：「给我找 2024 年以来财务部发布的关于差旅费报销的通知」
  → 提取结构化约束：
     {
       keywords: ["差旅费报销", "通知"],
       filters: {
         department: "财务部",
         publishDate: { $gte: "2024-01-01" },
         documentType: "通知"
       }
     }
  → 检索时先用 metadata filters 过滤，再做向量检索
```
**解决问题**：用户 Query 含明确的元数据约束，纯语义检索无法过滤

**落地建议**：
- 多轮对话场景：必须做「引用补全」
- 复杂问题场景：子问题拆解 + 子查询并行检索 + 结果合并
- FAQ/知识库场景：Query 扩写 + HyDE 提升召回
- 元数据丰富场景：结构化提取 + filter 前置过滤

## 五、RAG 架构设计

### Q13 🟡 请设计一个工业级 RAG 系统的架构，说明各模块职责。

**考察点**：RAG 全链路架构设计能力

**参考答案**：

```
┌─────────────────────────────────────────────────────────────────┐
│                      离线构建链路（Ingestion）                    │
│                                                                   │
│  文档源 (S3/本地/Confluence)                                      │
│      ↓                                                            │
│  文档加载器 (PDF/MD/HTML/OCR)  → 元数据提取（来源/时间/分类）    │
│      ↓                                                            │
│  清洗 & 去重（去 HTML 标签/模板内容/广告）                        │
│      ↓                                                            │
│  分块器（结构化优先 + overlap + 父子分块）                        │
│      ↓                                                            │
│  Embedding 模型 → 向量 + 原文 + 元数据 → 写入向量数据库 + 关键词索引│
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│                      在线查询链路（Query）                        │
│                                                                   │
│  用户 Query + 对话历史                                             │
│      ↓                                                            │
│  Query 改写层（引用补全 / 子问题拆解 / HyDE / 扩写）              │
│      ↓                                                            │
│  多路召回层（BM25 + 向量 + 结构化 filter）                        │
│      ↓                                                            │
│  RRF 融合 → Rerank 精排（Cross-Encoder）                         │
│      ↓                                                            │
│  上下文压缩层（去冗余 / 去重 / Extractive QA 抽关键句）           │
│      ↓                                                            │
│  Prompt 组装（System + 引用片段 + 对话历史 + Query）             │
│      ↓                                                            │
│  LLM 生成 → 答案 + 引用来源链接                                   │
│      ↓                                                            │
│  答案校验（Faithfulness Check：答案是否都来自上下文？）           │
└─────────────────────────────────────────────────────────────────┘
```

**核心模块职责**：

| 模块 | 职责 |
|------|------|
| **文档加载器** | 格式适配 + 增量同步（监听文件变更，避免重建整个库） |
| **分块器** | 结构化优先 + 可配置 chunkSize/overlap + 支持父子分块 |
| **Embedding 服务** | 统一模型接口，支持多模型切换；GPU 推理加速；批量 Embedding 优化 |
| **向量数据库** | 支持 ANN 索引 + Metadata Filter + 批量写入 + 增量更新 |
| **查询改写层** | 多轮引用补全（必做）+ 子问题拆解（复杂问题）+ 其他可选 |
| **召回融合** | RRF 融合多路召回结果 |
| **Reranker** | Cross-Encoder 精排 50-100 候选 → Top20 |
| **上下文压缩** | 压缩到 LLM 可容纳的上下文窗口内，尽量保留高信息密度片段 |
| **答案校验** | Faithfulness Check：LLM 自我校验或 NLI 模型校验答案忠实度 |

### Q14 🔴 当知识库文档量从 1 万增长到 1 亿（10000 倍），RAG 系统各层会遇到什么瓶颈？如何演进？

**考察点**：RAG 可扩展性设计

**参考答案**：

分阶段瓶颈与演进：

#### 阶段 1：1 万 ~ 10 万文档（单机可搞定）
```
存储：FAISS / Chroma 本地索引文件，单机内存能装下
检索：单路召回 + Rerank，延迟 < 200ms
瓶颈：基本无，随便玩
```

#### 阶段 2：10 万 ~ 1000 万文档（分布式向量数据库）
```
新瓶颈 1：单机内存装不下索引了
  → 方案：分布式向量数据库（Milvus / Qdrant / Weaviate）
     - 数据分片（Sharding）：按文档 ID 哈希分到多个节点
     - 副本（Replication）：多副本容错 + 读负载均衡
     - 数据量：每节点建议 < 1 亿向量（128 维 × 4 字节 ≈ 每向量 512 字节，1 亿 ≈ 50GB，单机能扛）

新瓶颈 2：Embedding 批量建库慢
  → 方案：并行化 Embedding
     - GPU 批量推理（batch size 拉满，如 256/512）
     - 多机多卡分布式 Embedding（Ray / Spark 分布式处理）
     - 增量建库：只 Embedding 新增/变更文档，而非全量重建
```

#### 阶段 3：1000 万 ~ 1 亿文档（查询侧优化 + 多租户）
```
新瓶颈 3：QPS 上来后向量数据库扛不住
  → 方案：查询侧优化
     - 查询缓存：Redis 缓存高频 Query 的检索结果（1-5 分钟 TTL）
     - 读写分离：主节点写入，从节点提供查询
     - 负载均衡 + 多副本：读请求均匀分发到副本节点

新瓶颈 4：单向量库精度下降（向量空间太拥挤）
  → 方案：前置分类路由，缩小检索范围
     - 用小模型先做 Query 分类（「这是问财务制度还是人事制度？」）
     - 分类后只在对应子库检索（财务子库 vs 人事子库），向量空间缩小 N 倍
     - 或 Metadata Filter 前置过滤（按部门/时间/文档类型过滤）

新瓶颈 5：Rerank 是慢操作，候选太多 rerank 延迟爆炸
  → 方案：分层 Rerank
     - 粗排：便宜快的小模型（bge-reranker-base）从 200 → 30
     - 精排：大模型（bge-reranker-large）从 30 → 10

新瓶颈 6：文档去重和版本管理
  → 方案：文档指纹去重（SimHash / MinHash），相同内容跳过建库
     - 文档版本管理：旧版本标记删除，新版本重新建索引
```

#### 阶段 4：1 亿 +（多模态 + 语义分层）
```
新瓶颈 7：跨语言/跨模态检索
  → 方案：统一多模态向量空间
     - 用 CLIP / ImageBind / BGE-M3 等多模态模型
     - 图文音视频统一 Embedding 到同一空间

新瓶颈 8：纯向量检索精度天花板
  → 方案：GraphRAG / 知识图谱增强
     - 从文档中提取实体和关系构建知识图谱
     - 检索时：向量召回实体 → 图谱推理扩展 → 关联文档补充
     - 适合复杂推理类问题（「A 公司和 B 公司有哪些合作项目？」）
```

### Q15 🟣 什么是 GraphRAG？它相比传统 RAG 在什么场景下有优势？如何实现？

**考察点**：GraphRAG 理解

**参考答案**：

**GraphRAG** = RAG + 知识图谱（Knowledge Graph）

传统 RAG 是「语义相似度匹配」——找与 Query 向量接近的文档片段；
GraphRAG 多了一层「结构化关系推理」——从文档中提取实体和关系，形成图谱，能做多跳推理。

**传统 RAG 的局限**（GraphRAG 能补这些）：
```
用户问：「字节跳动创始人张一名下投资了哪些 AI 公司？」
传统 RAG 需要：
  文档里刚好有完整句子「张一投资了 X 公司」才能召回
但如果：
  文档 A 说：「字节跳动由张一创立」
  文档 B 说：「张一通过 Y 基金投资了 AI 公司 Z」
  文档 C 说：「Y 基金另一笔投资投向了 W 公司，W 专注于大模型」
传统 RAG 搜单句都搜不完整 → GraphRAG 能：
  抽取实体：{张一, 字节跳动, Y基金, Z公司, W公司, 大模型}
  抽取关系：{张一, 创立, 字节跳动}, {张一, 控制, Y基金}, {Y基金, 投资, Z公司}, {Y基金, 投资, W公司}, {W公司, 领域, 大模型}
  → 多跳推理：张一 → 控制 Y基金 → 投资 (Z公司, W公司) → W公司领域=大模型
  → 回答：投资了 Z 公司和 W 公司（专注于大模型）
```

**GraphRAG 优势场景**：
1. **需要多跳推理的复杂问题**（A 与 B 的关系？哪些公司同时满足 X 和 Y 条件？）
2. **实体密集型文档**（财报、法律文件、新闻资讯，大量人名/公司名/地名）
3. **跨文档关联问答**（答案分散在多个文档，需要拼起来推理）

**GraphRAG 实现流程**（简化版）：

```
Step 1 离线建图：
  文档 → 分块 → LLM 抽取（实体, 关系, 实体类型）→ 构建图谱
  例：「字节跳动由张一创立于 2012 年」
    → 实体：{id:E1, name:字节跳动, type:公司}, {id:E2, name:张一, type:人物}
    → 关系：{src:E2, rel:创立, dst:E1, attrs:{year:2012}}

Step 2 实体 Embedding：
  每个实体（如「字节跳动」）做 Embedding，写入向量数据库
  每条文档 chunk 记录「提及了哪些实体」（倒排索引）

Step 3 在线检索：
  3.1 从 Query 抽取实体：「字节跳动投资了哪些 AI 公司？」
    → 抽取实体候选：字节跳动
    → 实体向量检索图谱中的匹配节点：找到 E1（字节跳动）
  3.2 图谱扩展：从 E1 出发做 1-3 跳游走，收集关联实体和关系
    → 跳 1：{张一, 创立, 字节跳动}, {字节跳动, 投资, X公司}, ...
    → 跳 2：{X公司, 领域, AI}, {Y基金, 投资, W公司}, ...
  3.3 召回关联文档：扩展到的实体 → 通过倒排索引找提到这些实体的文档 chunk
  3.4 和向量检索的结果做融合排序 → Rerank → 生成
```

**挑战与取舍**：
- **抽取质量**：LLM 抽取的实体和关系有噪声，需人工校验或后处理。实体消歧（「张一」 vs 「张一鸣」）是硬骨头
- **成本高**：每个 chunk 都要让 LLM 抽取三元组，成本明显高于纯向量
- **收益场景有限**：纯 FAQ 类问题（「如何重置密码？」）GraphRAG 收益很小，纯 RAG 够用
- **结论**：不要为了用而用。当你的问答场景中「复杂多跳推理 + 跨文档关联」占比 > 30% 时再考虑引入 GraphRAG

## 六、Prompt 工程与上下文注入

### Q16 🟡 设计 RAG 的 System Prompt 时，哪些要素必不可少？

**考察点**：RAG Prompt 设计能力

**参考答案**：

一个合格的 RAG System Prompt 必须包含以下要素：

```markdown
# 角色定义
你是一名 XX 领域的专业助手，擅长基于提供的文档准确回答用户问题。

# 核心约束（最重要，防止幻觉）
1. 你的回答必须严格基于【参考文档】中的内容，不可以编造文档中没有的信息。
2. 如果【参考文档】中没有相关信息，或者信息不足以回答问题，请直接说「抱歉，我没有找到足够的信息来回答这个问题」，不要猜测。
3. 如果【参考文档】中的内容存在矛盾，请向用户说明情况，并指出不同的说法来自哪里。
4. 禁止输出你自己的观点或建议，只陈述文档中的客观事实。

# 回答格式要求
1. 优先直接回答问题的核心，不要多余客套话。
2. 回答中引用到的每一条信息，请在句末标注引用来源，如 [1]。
3. 如果回答包含多个要点，用列表形式分点作答。
4. 遇到数据、日期、金额等，请保留文档中的精确表述，不要四舍五入。

# 参考文档格式
以下是检索到的参考文档，每条用 [序号] 标注了来源：
【参考文档开始】
{context}
【参考文档结束】
```

**关键设计点**：

1. **角色锚定**：限定在特定领域，减少模型发散到通用知识
2. **严格约束**：明确「不知道就说不知道」，**不要自己编**
3. **引用标注**：要求标注来源序号，便于用户点链接跳原文核验
4. **矛盾处理**：告诉模型遇到矛盾文档怎么办（而非让它自己瞎选）
5. **格式约束**：列表、精确数字、无废话，让输出结构化

**进阶技巧**：

**Few-shot 示例（应对格式不稳定）**：
```markdown
# 示例
用户：Q2 销量最高的产品是什么？
参考文档：[1] 产品 B Q2 销量 180；[2] 产品 A Q2 销量 150；[3] 产品 C Q2 销量 90
回答：
Q2 销量最高的产品是产品 B，销量为 180 [1]。

用户：怎么开红酒？
参考文档：[1] 公司差旅报销流程；[2] 采购管理制度
回答：
抱歉，我没有找到足够的信息来回答这个问题。
```

**结构化输出（让前端好渲染）**：
```markdown
# 输出必须是 JSON 格式
{
  "answer": "回答文本，带引用标注",
  "citations": [
    {"id": 1, "source": "文件路径或URL", "quote": "原文引用片段"}
  ],
  "hasEnoughInfo": true
}
```

### Q17 🔴 什么是 Lost in the Middle（中间遗忘）？在 RAG 中如何缓解？

**考察点**：上下文窗口注意力机制理解

**参考答案**：

**Lost in the Middle 现象**：
LLM 对上下文开头和结尾的内容注意力更强，中间位置的内容容易被忽略。

研究表明：把最相关的文档放在上下文中间，LLM 用不到它的概率明显更高（正确率下降 10-20%）。

```
上下文结构：
[System Prompt]  ← 注意力强
[文档 1: 无关]   ←
[文档 2: 最相关] ← 中间位置，容易被忽略 ❌
[文档 3: 相关]   ←
[文档 4: 无关]   ←
[用户问题]       ← 注意力强
```

**缓解策略**：

**策略 1：相关文档「置顶 + 置尾」，不要放中间**
```
Rerank 后的结果顺序：[1(最相关), 2, 3, 4, 5(最不相关)]

喂给 LLM 前，重新排序：
[1(最相关), 3, 4, 5, 2(次相关)]
  ↑                       ↑
  置顶                   置尾

这样最相关的文档既出现在开头也出现在结尾附近，命中率最高。
```

**策略 2：减少上下文长度，提高信噪比**
- 不要无脑塞 Top20 文档 → 用上下文压缩把每个文档压缩到关键句
- 控制总上下文 token 数：不要超过 LLM 窗口的 40%（留空间给推理）
- 每个 chunk 只保留与 Query 最相关的句子（Extractive Compression，让 LLM 或小模型从 chunk 中抽 1-2 句最相关的）

**策略 3：多次推理 + 分治**
```
问题复杂、需要参考的文档太多时，不要一次性塞进去：
方案 A - 分块回答：把文档分组，每组让 LLM 出一个「阶段性回答」，最后再让 LLM 基于阶段性回答总结
方案 B - Self-Ask：让 LLM 判断「我还需要哪些额外信息？」→ 多轮检索补充，而不是一次塞完
```

**策略 4：引用校验（Answer with Citations）**
- Prompt 中要求模型输出答案时必须标注每个论断的引用编号 [1] [2]
- 模型为了标注准确，会更仔细地扫描全文找来源，减少跳过中间内容的概率
- 生成后再做 Faithfulness Check：答案中的每条断言，是否真的在标注的引用中存在？

## 七、评估与优化

### Q18 🟡 RAG 评估的核心指标有哪些？分哪几层？

**考察点**：RAG 评估体系

**参考答案**：

RAG 评估分三层：**检索质量 → 生成质量 → 端到端质量**

```
用户 Query
    ↓
[检索层评估]  文档召回是否准确？
    ↓  通过了才谈生成
[生成层评估]  LLM 基于上下文生成的回答是否忠实、切题？
    ↓
[端到端评估]  用户是否满意？
```

### 1. 检索层指标（是否找到了正确的文档）

| 指标 | 含义 | 计算方式 |
|------|------|----------|
| **Recall@K** | 正确文档是否在 TopK 召回中 | 在 TopK 中找到了至少一个正确文档的 Query 占比。例：100 个 Query，85 个在 Top5 中有正确文档 → Recall@5 = 85% |
| **Precision@K** | 召回的 TopK 中有多少是相关的 | TopK 中相关文档数 / K。例：召回 5 个文档其中 3 个相关 → Precision@5 = 60% |
| **MRR**（Mean Reciprocal Rank） | 第一个正确文档排名的倒数平均值 | 第 1 名命中 → 1/1 = 1；第 2 名命中 → 1/2 = 0.5；第 5 名命中 → 1/5 = 0.2；全部 Query 平均 |
| **NDCG@K** | 考虑了排序位置加权的综合指标 | 相关度越高、排越前面，分数越高。适合有多级相关性标注的场景（完全相关/部分相关/不相关） |

**核心实践**：Recall@5 是最常用的门槛指标，工业界目标通常 ≥ 90%。召回不够，后面再怎么生成都没用。

### 2. 生成层指标（答案质量）

| 指标 | 含义 | 评估方式 |
|------|------|----------|
| **Faithfulness（忠实度）** | 答案中的每一条论断是否都能在上下文中找到依据？有无幻觉？ | LLM-as-Judge：让评审模型检查「答案中的每个事实是否都出现在参考文档中」，输出 yes/no 比例。或用 NLI（自然语言推理）模型批量判定 |
| **Answer Relevance（答案相关性）** | 答案是否回答了用户的问题？有没有答非所问？ | LLM-as-Judge：给（Query, Answer）打分 1-5，看是否切题 |
| **Context Precision** | 生成中实际用到的文档，在检索排序中排得靠前吗？ | LLM 标注答案中用到了哪些文档片段，看它们在召回结果中的平均排名位置 |

### 3. 端到端用户体验指标

| 指标 | 含义 |
|------|------|
| **正确率 / 采纳率** | 人工抽检答案是否正确；用户是否点击「赞」或复制了答案 |
| **拒答准确率** | 不该答的问题（无信息）是否真的拒答了，而不是瞎编 |
| **端到端延迟** | 从用户提交到首个 token 返回（TTFT） + 生成完整答案（TPOT） |
| **归因点击** | 用户点击引用链接跳原文的比例（越高说明用户需要验证，也说明引用有用） |

### Q19 🔴 什么是 LLM-as-Judge？用 LLM 评估 RAG 有什么陷阱？如何规避？

**考察点**：评估方法的可靠性

**参考答案**：

**LLM-as-Judge**：用一个强模型（如 GPT-4、Claude Opus）作为「评审员」，给 RAG 的检索/生成质量打分。

典型评审 Prompt 模板：
```markdown
你是一名专业的答案质量评审员，请基于以下信息给答案评分：

【用户问题】
{query}

【参考上下文】
{context}

【待评估答案】
{answer}

请从两个维度打分（1-5 分），并给出理由：
1. 忠实度（Faithfulness）：答案是否完全基于参考上下文，没有编造？
   - 5: 完全忠实，每句话都有依据
   - 1: 大量编造内容

2. 相关性（Relevance）：答案是否准确回答了用户问题？
   - 5: 完美回答，清晰完整
   - 1: 完全答非所问

输出 JSON：{"faithfulness": 分数, "faithfulness_reason": "", "relevance": 分数, "relevance_reason": ""}
```

**陷阱与规避**：

| 陷阱 | 问题 | 规避方法 |
|------|------|----------|
| **位置偏见** | Judge 模型倾向于给排在前面的答案高分 | 随机打乱待评估答案的顺序；多次评估取平均 |
| **Verbosity 偏见** | Judge 倾向于给更长、更啰嗦的答案高分（即使没干货） | 评分 rubric 中明确「无废话、简洁」比「啰嗦」分高；或让 Judge 先提取关键论断再比对 |
| **模型自带知识干扰** | Judge 可能用自己的知识来判断对错，而不是看给定的上下文 | Prompt 中反复强调「必须严格只看参考上下文，不要用你自己的知识」；上下文故意写错信息看 Judge 是否按上下文评判 |
| **打分方差大** | 同一条答案两次评估可能给出不同分 | 多次评估取平均分（如 3 次取众数/均值）；用结构化 rubric 减少主观；配合小部分人工标注校准 |
| **一致性差** | 不同 Judge 模型（GPT-4 vs Claude）打分分布不同 | 固定 Judge 模型和版本；用一批金标数据校准 Judge 的分数映射（如 GPT-4 打 3 分对应人工几分） |
| **成本高** | 每条样本调 GPT-4 评估很贵 | 分层评估：大量样本先用便宜的小模型（或 BGE Reranker 当 proxy）筛选出困难样本，再用 GPT-4 精评困难样本 |

**最佳实践**：
1. **金标集打底**：至少 200-500 条人工标注的（Query, 正确文档, 参考答案），用来校准 Judge 模型
2. **Judge 相关性校验**：对同一批样本，对比 Judge 打分和人工标注的 Spearman 相关系数（≥ 0.8 算可用）
3. **不要全信自动化评分**：高风险场景 + Judge 打分边界的样本（如忠实度 3 分）要人工抽检
4. **回归测试**：Judge 评分集成到 CI，版本升级后跑评估集，看是否比基线掉分

## 八、高级 RAG 技术

### Q20 🟡 什么是 Self-RAG / Corrective RAG / Adaptive RAG？它们的核心思路是什么？

**考察点**：RAG 自我纠错/自适应范式

**参考答案**：

传统 RAG 是「检索 → 生成」的固定流水线；这些高级 RAG 的核心思路是让 LLM 自己做「元决策」——决定是否需要检索、检索结果够不够、要不要重试检索。

#### 1. Self-RAG（自我反思 RAG）
在生成过程中插入自我评估 token，让模型自己判断是否需要检索、检索结果是否有用。

```
用户 Query
    ↓
LLM 自我反思：「回答这个问题我需要外部知识吗？」
  ├─ 不需要 → 直接回答（模型自身知识足够）
  └─ 需要 → 检索 → 拿到文档 →
      LLM 再反思：「检索到的文档有用吗？」
        ├─ 有用 → 基于文档回答
        └─ 没用 → 丢弃 / 改写 Query 再检索一次
回答 + 引用
```

**价值**：减少不必要的检索（用户问「1+1=?」这种常识就别浪费检索开销）；低质量检索结果会被丢弃，避免误导生成。

#### 2. Corrective RAG（纠错 RAG，CRAG）
在「检索」和「生成」之间加一个「文档质量评估器」：

```
Query → 检索 → TopK 文档
                ↓
       文档质量评估（分类器 / LLM）
                ├─ 全部无关 → Web 搜索补充（或扩写 Query 重检）
                ├─ 部分相关 → 保留相关部分，无关部分丢弃
                └─ 全部相关 → 继续
                         ↓
                    生成回答
```

**价值**：本地知识库不全时自动降级到 Web Search；不会让垃圾文档污染生成。

#### 3. Adaptive RAG（自适应 RAG）
把「用不用 RAG」「用哪种 RAG 策略」的决策权交给路由模型：

```
用户 Query
    ↓
路由 LLM 分类（Query 属于哪类？）
  ├─ 简单常识类 → 直接走 LLM（不需要 RAG，省成本）
  ├─ 简单知识类 → 走「基础 RAG」（召回 TopK + 生成，够用了）
  ├─ 复杂推理类 → 走「高级 RAG」（子问题拆解 + 多轮检索 + Self-RAG 反思）
  └─ 无答案类 → 直接拒答（别瞎检索）
```

**价值**：不同 Query 用不同复杂度的策略，成本和质量平衡最优。简单问题省 50% 开销，复杂问题给足算力保证质量。

### Q21 🔴 多模态 RAG（图文/音视频）相比纯文本 RAG 有哪些特殊挑战？如何解决？

**考察点**：多模态 RAG 能力

**参考答案**：

**多模态 RAG 典型场景**：
- 产品手册（图文混排）：问「这个按钮在哪？」→ 既要理解文字也要理解示意图
- 教学视频：问「第 2 章 PPT 里写的公式是什么」→ 要从视频帧和音频转录中联合检索
- 医疗影像报告：问「这张 CT 有什么异常？」→ 要向量化图片本身，而非仅报告文字

**特殊挑战与方案**：

| 挑战 | 问题 | 解决方案 |
|------|------|----------|
| **模态对齐**：图片和文本的向量不在同一空间，「猫的图片」和「猫的文字」向量不近 | 用纯文本 Embedding 搜不到图片 | **多模态 Embedding 模型**：CLIP / BLIP / BGE-M3 / 通义千问多模态，这些模型在图文对齐数据集上训练，把图文映射到同一向量空间 |
| **图片比文字信息密度高**，一张图可能包含多个主题，整图 Embedding 太稀释 | 一张包含手机+手表+耳机的图，单独搜「耳机」匹配度低 | **图片分块 / 区域检测**：用目标检测模型把图片切成多个语义区域（如「手机区域」「耳机区域」），每个区域单独 Embedding + 存整图引用 |
| **无法直接引用图片**：纯文本可以「[1] 引用第 3 句」，图片怎么引用？ | 用户无法验证答案来源是否正确 | 保留图片分块的坐标信息 + 原图链接；答案中引用时附带图片缩略图 + 位置标注（如「图中红色框区域标注的是电源键」） |
| **视频时空检索**：用户问的是视频某个时间点的内容 | 整视频 Embedding 找不到精确时刻 | **视频切片**：按 10-30 秒切分，每帧抽关键帧 → 关键帧 Embedding + 音频转录 Embedding，两路融合检索；返回结果带时间戳，播放器可直接跳 |
| **表格 / 图表理解难**：柱形图的数值、表格的行列关系，纯文本描述丢失信息 | 「Q2 哪个产品销量最高？」从图片描述中难直接答 | **方案 1**：OCR + 结构化提取（图表转数字表格文本）<br>**方案 2**：生成阶段用多模态 LLM（GPT-4o / Claude 3.5 Sonnet）直接看图理解，而非仅用纯文本 LLM 读描述 |

**多模态 RAG 流水线示例**：
```
离线建库：
  视频 → 每 10 秒抽 1 关键帧 + 音频转文字
    关键帧 → CLIP Embedding + Caption 生成（「画面显示了一个人正在讲解 PPT，标题是 RAG 架构」）
    音频转文字 → 分块 Embedding
```

## 九、工程实践

### Q22 🟡 RAG 建库时如何避免全量重建？增量同步有哪些方案？

**考察点**：工程化能力

**参考答案**：

**全量重建的问题**：
- 10 万文档建库可能需要数小时（Embedding + 索引构建）
- 每次全量重建浪费计算资源
- 新文档上线延迟高（必须等下一次全量）

**增量同步方案**：

#### 方案 1：基于修改时间的定时扫描（最简单）
```
文档元数据表：
  doc_id | doc_path | last_modified | last_indexed_at

定时任务（每 5 分钟）：
  1. 扫描 last_modified > last_indexed_at 的文档
  2. 对新/改文档重新分块 + Embedding → upsert 到向量库
  3. 扫描已被删除的文档 → 删除对应向量
  4. 更新 last_indexed_at = now()

优点：实现简单，不依赖外部消息系统
缺点：扫描有延迟（分钟级）；需要遍历文件元数据，量大时慢
```

#### 方案 2：事件驱动 + 消息队列（生产级）
```
文档上传服务 → 发布事件（DocCreated / DocUpdated / DocDeleted）到 Kafka
                  ↓
              建库消费者消费：
                - DocCreated: 分块 + Embedding + 写入
                - DocUpdated: 先按 doc_id 删旧 chunks → 再写新 chunks
                - DocDeleted: 按 doc_id 删除所有关联 chunks

优点：实时性好（秒级）；增量处理不会重复扫描
缺点：依赖消息队列；需要保证事件不丢（至少一次消费 + 幂等）
```

#### 方案 3：版本号 + 双写切换（大版本升级用）
```
场景：Embedding 模型升级了，必须全量重建，但不想停服务
  1. 新建一个 collection_v2
  2. 后台全量把所有文档用新模型 Embedding 写入 collection_v2
  3. 写完后做完整性校验（对比 v1 和 v2 的文档数、抽样召回质量）
  4. 校验通过 → 查询流量切换到 v2（原子切换）
  5. 观察 24h 稳定 → 删除 v1

优点：零停机升级；回滚方便（切回 v1 就行）
缺点：双倍存储成本；需要两套环境并行一段时间
```

**关键工程细节**：

1. **幂等写入**：同一文档重复消费不能产生重复数据。向量数据库 upsert（按 chunk_id 覆盖写入）
2. **chunk_id 生成规则**：`hash(doc_id + chunk_start + chunk_end)`，稳定可重算
3. **删除机制**：不要物理删除（慢），用 metadata 标记 `deleted=true` + filter 过滤；定期清理
4. **一致性校验**：每日离线比对「文档源总数」和「向量库非 deleted 的 chunk 数」，发现不一致告警
5. **失败重试**：Embedding 调用失败用指数退避重试；死信队列收失败文档，人工处理

### Q25 🟣 设计一个「代码仓库智能问答 RAG」，用户能问「XXX 函数怎么用？」「XXX 报错是什么原因？」，给出关键设计。

**考察点**：代码特化 RAG 设计

**参考答案**：

代码和自然语言文档有本质差异：AST 结构、调用关系、符号引用、分块方式不同。

**架构要点**：

```
离线构建：
  代码仓库 → Clone → 语法解析
    ├─ AST 解析（Tree-sitter / LSP）
    │    ├─ 函数/类级符号：函数名、签名、参数、返回值、所在文件、行号
    │    ├─ 调用关系图：function A 调用了 B、C、D
    │    └─ 继承关系：class X extends Y
    ├─ 分块：
    │    ├─ 函数级 chunk（每个函数一个 chunk，附上函数签名和上下文）
    │    ├─ 文件级 chunk（文件顶部注释 + import + 导出符号）
    │    └─ 目录级 chunk（README + 模块概述）
    ├─ Embedding：
    │    代码 Embedding 模型（CodeBERT / StarCoder Embedding / 代码微调的 BGE）
    │    + 普通文本 Embedding（处理注释和 README）
    ├─ 索引：
         符号倒排索引（函数名 → 定义位置）→ 精确符号检索
         向量索引（函数体 + 注释 Embedding）→ 语义检索
         调用关系图（GraphRAG 用）

在线查询：
  用户：「aipack 的 Contextual Query Rewrite 在哪实现的？我想参考一下」
    ↓
  Query 分析：
    - 提取符号关键词：Contextual Query Rewrite（可能是函数/类名）
    - 提取语义意图：想找实现位置，用于参考
    ↓
  多路召回：
    1. 符号检索（精确匹配）：「Contextual」模糊匹配函数名 → 找到 `contextualRewrite()`
    2. 向量检索（语义匹配）：用户描述 → 向量匹配注释和文档
    3. 文件路径模糊匹配：文件名含 `rewrite` / `query`
    ↓
  融合 + Rerank → 取 Top 10
    ↓
  图扩展（GraphRAG 增强）：
    如果命中了 `contextualRewrite()`，自动把它「调用的函数」和「被谁调用」也附在上下文
    → 用户不只是拿到函数本体，还知道它在链路中的位置
    ↓
  生成 Prompt 组装（特殊格式）：
    System Prompt 要求：回答代码问题时，必须给出文件路径、行号、函数签名
    代码片段附语言标记，避免语法错
    ↓
  LLM 生成 → 返回：
    功能说明 + 代码位置（可点击跳转 IDE）+ 调用关系示例 + 使用示例
```

**关键设计点**：

1. **分块策略必须是语法感知的（AST-aware）**，不能按 500 字符硬切：
   - 切在函数中间 = 函数体残缺 = Embedding 没用
   - Tree-sitter 支持 50+ 语言的语法解析，按函数/类/方法边界切分
   - 每个函数 chunk 附带上层上下文（所属类名、所属模块名、import 依赖）

2. **符号索引必不可少**：
   - 程序员搜代码最常用「函数名/类名」精确匹配（如找 `createRequire`）
   - 纯向量检索对精确符号匹配效果差（大小写、下划线差异容易误匹配）
   - 必须有倒排索引：`symbol_name(lowercase) → list of definitions`

3. **Embedding 模型要选代码特化的**：
   - 普通文本 Embedding（BGE / OpenAI）能看懂注释，但不懂 `def foo(x: int) -> str:` 的语义
   - 代码 Embedding：CodeBERT / CodeT5+ / StarCoder Embedding / Salesforce CodeGen Embeddings

4. **引用跳转**：
   - 答案中的代码引用直接生成 IDE 跳转链接（如 `vscode://file/path/to/file.py#L10-L20`）
   - 点击直接跳到对应行，用户不用手动搜

5. **常见场景增强**：
   - 「XX 报错怎么回事？」→ 加错误日志倒排 + 异常类关联到处理函数的引用
   - 「XX 函数怎么调用？」→ 返回函数签名 + 调用示例（从调用关系图里找真实调用代码作为 Example）

## 十一、编码题

### Q26 🟡 实现一个 RRF（Reciprocal Rank Fusion）函数，融合多路召回结果。

```typescript
interface SearchResult {
  id: string;
  score: number; // 原始分数，融合时可能用不到
  content?: string;
}

/**
 * RRF 融合多路召回结果
 * 公式：score(doc) = Σ 1 / (k + rank_i)，k 默认 60
 * rank_i 是该 doc 在第 i 路召回中的排名（从 1 开始，未召回则该路贡献 0）
 */
function rrfFusion(
  resultsList: SearchResult[][], // 多个召回列表，每个内部已按分数降序排好
  options: { k?: number; topK?: number } = {}
): SearchResult[] {
  const k = options.k ?? 60;
  const topK = options.topK ?? 10;

  const scoreMap = new Map<string, { doc: SearchResult; score: number }>();

  // 遍历每一路召回
  for (const results of resultsList) {
    results.forEach((doc, index) => {
      const rank = index + 1; // 排名从 1 开始
      const rrfScore = 1 / (k + rank);

      const existing = scoreMap.get(doc.id);
      if (existing) {
        existing.score += rrfScore;
      } else {
        scoreMap.set(doc.id, { doc, score: rrfScore });
      }
    });
  }

  // 按融合分数降序排序，取 TopK
  return Array.from(scoreMap.values())
    .sort((a, b) => b.score - a.score)
    .slice(0, topK)
    .map(({ doc, score }) => ({
      ...doc,
      score, // 覆盖原始分数为融合分数
    }));
}

// 使用示例
const bm25Results: SearchResult[] = [
  { id: 'a', score: 8.2 },
  { id: 'b', score: 7.5 },
  { id: 'c', score: 6.1 },
];
const vectorResults: SearchResult[] = [
  { id: 'b', score: 0.95 },
  { id: 'd', score: 0.92 },
  { id: 'a', score: 0.88 },
];

const fused = rrfFusion([bm25Results, vectorResults], { topK: 5 });
// 预期：a 和 b 都出现两次，排名综合更靠前
// a: rank1=1 + rank3=3 → 1/61 + 1/63 ≈ 0.01639 + 0.01587 = 0.03226
// b: rank2=2 + rank1=1 → 1/62 + 1/61 ≈ 0.01613 + 0.01639 = 0.03252 ← 更高，排第一
```

**要点**：
- RRF 不看原始分数，只看排名（避免不同算法量纲差异）
- `k` 常取 60，影响排名 1 和排名 2 的差距大小；k 越小，头部排名差距越放大
- 多路融合天然支持去重（同 id 累加分数）
- 未在某路召回中出现的文档，该路贡献 0 分

### Q27 🔴 实现一个简单的「上下文引用补全」函数：把多轮对话中带指代的当前 Query，改写为独立的完整查询。

```typescript
interface Message {
  role: 'user' | 'assistant';
  content: string;
}

/**
 * 把多轮对话中带指代的当前问题改写为上下文无关的独立问题

 *   history: [

 *   ]

 *   → 输出: "RAG 分块中 overlap 的最佳设置是多少？"
 *
 * 实现用 LLM 完成改写，这里实现 orchestration 逻辑 + fallback 策略
 */
async function rewriteContextualQuery(
  history: Message[],
  currentQuery: string,
  options: {
    llmCall: (prompt: string) => Promise<string>;
    maxHistoryRounds?: number; // 只看最近 N 轮
    maxRewrittenLength?: number; // 改写后太长截断

  const {
    llmCall,
    maxHistoryRounds = 4,
    maxRewrittenLength = 200,

  // 1. 只取最近 N 轮对话（避免 prompt 过长 + 更聚焦当前话题）
  const recentHistory = history.slice(-maxHistoryRounds * 2);

  // 2. 如果历史为空，直接返回原 Query（无需改写）
  if (recentHistory.length === 0) {
    return currentQuery;
  }

  // 3. 构造改写 Prompt
  const historyText = recentHistory
    .map(m => `${m.role.toUpperCase()}: ${m.content}`)
    .join('\n');

  const rewritePrompt = `你是一名对话查询改写助手。
任务：把用户最后一个问题中的指代（如「这个」「那个」「它」「那」「上面提到的」等）替换为完整的上下文信息，
使问题脱离对话历史也能被独立理解。

要求：
1. 只改写有指代或省略的部分，原意保持不变
2. 如果原问题已经不需要上下文（是独立完整的问题），直接返回原问题
3. 输出改写后的问题，不要多余解释
4. 改写后不要超过 ${maxRewrittenLength} 个字符

对话历史：
${historyText}

用户当前问题：${currentQuery}

改写后的问题：`;

  // 4. 调用 LLM 改写，带容错
  try {
    const rewritten = await withTimeout(llmCall(rewritePrompt), 3000);

    // 5. 基本校验：避免 LLM 乱来
    if (!rewritten || rewritten.trim().length === 0) {
      return currentQuery; // 失败 fallback
    }
    // 如果改写后明显包含错误前缀（如「改写后的问题：」），清洗掉
    const cleaned = rewritten
      .replace(/^改写后的问题[：:]/i, '')
      .replace(/^答[：:]/, '')
      .trim();

    // 6. 长度保护
    return cleaned.slice(0, maxRewrittenLength);

  } catch (err) {
    // LLM 失败 / 超时 → 安全 fallback：把历史拼在问题前面
    // 至少能让检索看到一些历史关键词
    console.warn('Rewrite failed, fallback:', err);
    const lastUserQuestions = recentHistory
      .filter(m => m.role === 'user')
      .map(m => m.content)
      .join('；');
    return `${lastUserQuestions}；${currentQuery}`.slice(0, maxRewrittenLength);
  }
}
```

**要点**：
- 改写后内容作为独立问题喂给检索层，解决「那它呢」之类的指代问题
- LLM 改写可能失败，必须有健壮的 fallback 策略（拼历史关键词保底）
- 只看最近 N 轮，避免 prompt 过长和混入过期上下文
- 清洗 LLM 输出的多余字符（前缀/后缀垃圾）
- 改写失败时不影响主流程，最多是检索精度下降一点点

## 十二、加分项 / 开放讨论

### Q28 🟡 你认为当前 RAG 最大的瓶颈是什么？未来 1-2 年 RAG 会如何演进？

**参考答案**：

| 瓶颈 | 现状问题 | 演进方向 |
|------|----------|----------|
| **分块精度** | 一刀切的 chunkSize 导致语义截断或稀释 | 动态分块：根据文档类型、内容密度自适应 chunk；语义边界检测；查询时动态组装父文档块 |
| **检索召回天花板** | 纯向量 + BM25 对复杂多跳推理问题无能为力 | 检索架构从「相似度匹配」升级为「检索 + 推理」：GraphRAG、Agentic RAG（Retrieval Agent 自主决定多轮检索什么） |
| **长上下文矛盾** | 上下文越长，LLM 越容易 Lost in the Middle / 成本高 | 分层记忆：RAG 作为「外部长期记忆」，LLM 上下文只放压缩后的核心信息；按需动态取更多 |
| **评估与优化闭环难** | RAG 优化靠经验，效果提升缺乏系统化方法论 | 自动化 Eval 平台：每次改 Prompt/Chunk/模型，自动跑评估集看指标变化，类似传统软件的 CI 测试 |
| **幻觉依然存在** | 即使有上下文，LLM 仍可能「复述时出错」或「过度推理」 | 校验层增强：Faithfulness Check 从「可选」变「必做」，答案逐条断言溯源到原文片段，生成后校验不过自动重试 |
| **成本高** | 建库 + Rerank + LLM 生成，每次问答几块钱 | 小模型替代：7B-13B 特化 Rerank/压缩/生成模型成本是 API 的 1/50；缓存命中率提升 |

**个人判断**（可结合项目经验展开）：
1. **Agentic RAG 是下一步主流**：从「一次性检索 + 一次生成」升级为「检索 Agent 自主规划多轮检索→判断是否足够→必要时再检索」的循环模式。对于复杂问题，这会成为默认范式。
2. **评估标准化**：现在各家评估都是各自写 Prompt，未来会出现类似 ImageNet 之于 CV 的行业标准 RAG 评测集 + 统一评估协议。
3. **结构化知识与非结构化融合**：GraphRAG / Text-to-SQL / 全文检索三条线合流，知识库既包含结构化数据库也包含非结构化文档，Query 路由到合适的引擎。

### Q29 🟡 Agentic RAG（让 Agent 自主规划检索）和传统 RAG 有什么区别？有什么价值？

**参考答案**：

**传统 RAG（流水线模式）**：
```
用户问 → 固定套路：改写检索 → 取 Top5 → 生成 → 返回
  缺点：
  - 问题需要多次检索才能收集全信息时，传统套路只做一次就放弃
  - 第一次检索到垃圾文档时，没有能力丢弃后换 Query 重检
```

**Agentic RAG（Agent 模式）**：
```
用户问 → Agent 循环：
  Thought: 我需要先找 A 类信息
  Action: search("A 关键词")
  Observation: 得到文档 1-5
  Thought: A 信息找到了，但还需要 B 的数据，文档 2 提到了 B 但不完整
  Action: search("B 关键词 补充")
  Observation: 得到文档 6-10
  Thought: 信息够了，我现在可以回答了
  Final Answer: ...
```

**核心区别**：
- 传统 RAG = 固定流水线，检索和生成各只做一次
- Agentic RAG = 决策循环，检索次数、查询词、是否需要更多信息，都由 Agent 自主决定

**价值**：
1. **复杂问题覆盖更全**：需要跨多个文档、多轮补充信息的问题，Agent 能反复检索收集
2. **检索失败有自检能力**：第一次检索到的文档如果没用，Agent 可以重写 Query 再来
3. **结构化问题解耦**：可以先 Text-to-SQL 查结构化数据库、再查非结构化文档、再查代码库——根据问题自主编排检索源

**代价与局限**：
- 成本高：多轮检索 + 多轮 LLM 推理，可能是传统 RAG 的 3-10 倍
- 延迟高：循环多轮，用户等待时间从 2s 变成 10s+
- 结论：简单问题用传统 RAG（快+省），复杂/深度问题走 Agentic RAG（准+全），通过 Query 难度分类器做路由。
